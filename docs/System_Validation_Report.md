## Validation methodology

Existing module/API regression evidence is summarized in the Unit Test Report. The supplemental [validate-system.cjs](testing/EMS-TEST-03/validate-system.cjs) harness starts the unchanged Express app and issues actual loopback HTTP requests; a tripwire prohibits database calls. It uses synthetic credentials only for JWT rejection checks and records zero database calls. This verifies request parsing, public endpoints, early validation, authentication guards and configured CORS headers; it does not log in real users or prove persistence.

Two compatibility checks execute the current registration validator against the literal payload extracted from the checked-in k6 script and compare the isolated preparer's exported migration allowlist with the repository migration files. They are tooling integration checks, not live load or database tests. The production build is an independent build check, not a browser acceptance test.

```powershell
& "$nodeRuntime/node.exe" docs/testing/EMS-TEST-03/validate-system.cjs
& "$nodeRuntime/node.exe" "$nodeRuntime/node_modules/npm/bin/npm-cli.js" --prefix frontend run build
```

Run these from the repository root after installing dependencies. The system harness returns exit code 1 because both compatibility assertions fail; this is an expected faithful defect record, not an infrastructure crash. No shared database is touched.
